The case for boring stacks

We shipped a 2026 production application without a build step, without a JavaScript framework, and without regret. Here is what the industry trades away every time it forgets that the platform itself is enough.

There is a reflexive pattern in modern web work that goes something like this: a new project starts, a developer opens a terminal, runs npm create something, and within an hour has installed eight hundred packages, a build system, a bundler, a transpiler, a CSS preprocessor, a component library, a state manager, a router, a testing framework, a development server, and a list of scripts long enough that the project's package.json is now the longest file in the repository. The application has not been written yet.

We started a project last year and decided not to do this. The stack is HTML, CSS, and a small amount of JavaScript served directly by a PHP application. Where we wanted reactive sprinkles in the interface, we used Alpine.js — a single script tag, no build step. There is no transpiler. There is no bundler. There is no node_modules directory in the production checkout. Editing a file and reloading the page is the development cycle.

The application is in production. It serves real users. It has TLS, end-to-end encrypted user content, push notifications, an authenticated multi-device session protocol, and a substantial PHP backend. Nothing about its capability is reduced by the absence of the modern build chain. What is reduced is the maintenance surface, the attack surface, and the amount of indirection between a change and the running result.

What "boring" buys

The first thing it buys is the ability to read your own code. Vanilla web fundamentals — HTML, CSS, the DOM API, and JavaScript without compilation — have been stable for the better part of a decade and will be stable for the foreseeable future. A file written today will run, without modification, on a browser five years from now. The same cannot be said with confidence about a file written in any of the major JavaScript frameworks during the same window.

The second thing it buys is independence from the build. When the build pipeline is the bottleneck, every change is mediated by tooling whose behavior the average developer does not fully understand. When something breaks — a stale cache, a transitive dependency upgrade, a quietly deprecated plugin — the failure is upstream of the code the developer wrote. The class of bugs that consume the most time, in our experience with previous projects, are not bugs in application logic. They are bugs in the system that produces the running application from the files on disk.

The third thing it buys is honesty about what the application is doing. Modern frontend stacks paper over an enormous amount of complexity in service of a developer ergonomic that is, charitably, a wash. The page that eventually reaches the browser is reconstructed from a cascade of compiled, minified, and tree-shaken modules whose origins in the source repository require tooling to trace. With vanilla code, the file you wrote is the file the browser is running. The connection between intent and execution is direct.

What it costs

It is not free. There are real things you give up.

You give up some component reuse. There is no equivalent in vanilla code to the ergonomics of a typed prop interface on a custom component. You can approximate it with web components, with templating partials, or with discipline, but none of those is as smooth as the framework version. For an application of moderate size built by a small team, the discipline turns out to be sufficient. For a sprawling application built by a rotating cast of engineers, it probably is not.

You give up the convenience of the modern type system. We wrote our backend in PHP and our frontend in plain JavaScript, neither of which gives us the static safety net that TypeScript and a strongly-typed framework would provide. We compensate with smaller modules, named functions, defensive parsing at boundaries, and tests on the parts that hurt when they break. Whether this is a good trade depends on the codebase. In ours, it has been.

You give up some social signals. There is a class of engineer whose first question about a project is which framework it uses, and the answer "none, we just write HTML" reads to them as a confession of insufficient seriousness. We have stopped finding this important.

The real argument

The real argument for the boring stack is not that frameworks are bad. They are not bad. They are sometimes — often — the right choice. The real argument is that the choice is rarely made. The default is to reach for the framework, the build system, the toolchain, the cloud-native pattern, the everything, and the question of whether any of it serves the specific problem in front of the developer goes unasked.

Every load-bearing decision in a software project should be re-derivable from first principles. Why this database? Why this language? Why this framework? Why this build system? If the answer is "because that is what people are using," that is not a justification, that is fashion. The cost of fashion in software is paid out in dependency upgrades, in build failures, in onboarding time, in documentation rot, in the slow accumulation of mystery complexity that makes a codebase a year old feel like it requires an archeologist to read.

Every load-bearing decision in a software project should be re-derivable from first principles. If the answer is "because that is what people are using," that is not a justification, that is fashion.

We are not advocating for a return to anything. The platform we are using is the modern platform: ES2022 JavaScript, modern CSS with custom properties and container queries, fetch, the IndexedDB API, the Web Crypto API, the service worker, WKWebView wrapped via Capacitor for the native iOS shell. None of this is old. What is old, in the relative sense, is the decision to use the platform directly rather than through a layer of abstraction.

We will use a framework when we encounter a problem that actually requires one. We have not encountered that problem yet. When we do, we will know, because the work will become harder rather than easier without one. Until then, the platform is enough.

For the next project

If you are starting a new project, here is the recommendation we would offer, with the caveat that it is the recommendation we would offer ourselves and not necessarily a universal prescription:

Try writing it without the build step first. Open index.html in an editor, write the code, open the file in a browser. Add only what you actually need, when you actually need it, with the bar set at "the platform truly cannot do this." You will be surprised, in 2026, how often the platform truly can.
